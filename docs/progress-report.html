1. Executive summary

The project is feature-complete against the blueprint's MVP definition (Section 15.1), and it is deployed and serving live traffic: the frontend on Vercel, the API and scheduler worker on Render, with a hosted language model configured in production so candidates are written by an LLM rather than by templates. A user can register, define a Monthly Plan, receive three ranked message candidates with transparent score breakdowns and full provenance, select/edit/reject one, watch the personalization engine update, and see the effect proven in analytics. The scheduler prepares each month's cycle automatically and sends T-3/T-1 reminders.

Verification status: 166/166 automated tests pass (including every golden value from Section 17), TypeScript typecheck and production build are clean, CI is green on Python 3.10 and 3.11 plus the frontend build, and the deployed application was exercised end to end — login → dashboard → review → feedback — against the live API. Production health reports llm_provider: groq, llm_model: openai/gpt-oss-120b, environment: production, and the git commit it is running.

6. The AI engine, concretely

Candidates are generated by a hosted language model — in production Groq serving openai/gpt-oss-120b, with openai/gpt-oss-20b and a Qwen model as automatic fallbacks if the account cannot call the primary. Every provider sits behind one adapter interface (Groq, Gemini, OpenAI, Anthropic, Ollama), each with its own circuit breaker, retry schedule (1 s, 3 s, 9 s with jitter), tolerant JSON parsing and cost metering.

ConcernBehaviour
Provider chainPrimary provider → any other configured hosted provider → (only if opted in) the template engine. A provider whose breaker is open is skipped, never retried in a loop.
Failure policyNo silent substitution. If every provider fails, the request is marked FAILED, the reason is stored on the request, the previous batch survives, and the UI says the regeneration failed.
Template fallback64 templates across 5 slot banks, used only with MM_ALLOW_TEMPLATE_FALLBACK=true. Template batches are labelled as such on the review screen — never presented as model output.
ProvenanceEach request stores provider, model, source (schedule, regenerate), creation time and any fallback reason.
Cost controlOne call per batch (six candidates), token metering and a monthly budget guardrail; no per-candidate calls.
DeterminismRanking is seeded (Monte-Carlo seed 42, Thompson RNG, tone training) so identical inputs and weights produce identical rankings even when the text itself varies.
Why this matters for the report: earlier revisions described the template engine as the default provider. That is no longer true. The template engine is now an explicit, opt-in safety net; production runs on a hosted model, and the review UI always states which produced the batch.
