2. Architecture (blueprint Section 13)

FRONTEND — Next.js 14 + TypeScript + Tailwind · Vercel
Dashboard · Create · Review/Compare · Calendar · Plans · History · Analytics · Settings — calls only the public API; no secrets in the browser
│ HTTPS / JSON — JWT access token + refresh cookie ▼
BACKEND API — FastAPI · Render
[Auth + RBAC] → [Validation] → [Routers (58 handlers / 45 paths)] → [Services] → [uniform error / JSON-logging layer]
▼
GENERATION + RANKING — app/ai/
preprocess + keywords → context + history retrieval → Thompson-sampled style arms → prompt → one hosted LLM call (6 candidates) → hard constraints + dedup → embeddings → features F, s = F·w → MMR top-3 → Monte-Carlo confidence → explanation payload
▼
DATABASE — SQLite (default) / PostgreSQL
16 tables: users, user_preferences, audience_profiles, topics, occasions, monthly_plans, post_cycles, generation_requests, generated_messages, feedback_events, tone_stats, scheduled_posts, post_metrics, notifications, job_runs, analytics_daily
▲
AUTOMATION — APScheduler worker · Render
daily cycle scan → enqueue generation → notify → T-3/T-1 reminders → catch-up → plan extension · job_runs audit · webhook tick for suspended hosts

Statelessness rule from the blueprint is respected: the API holds no in-memory user state, so it can run behind several instances; the worker shares the same code and database but starts with a different command (python -m app.scheduler.runner). The only in-memory state that matters — circuit breakers and the scheduler tick lock — is deliberately per-process.

3.3 Security

  • Argon2id password hashing (argon2-cffi), tuned parameters, constant-time compare.
  • JWT access (15 min) in memory + refresh (14 days) in an httpOnly cookie (SameSite=None; Secure in production); silent refresh in the API client hides 401s.
  • Signed ICS calendar token so subscription URLs work without a login; constant-time-compared webhook token for scheduler/seed endpoints.
  • Uniform error envelope {error: {code, message, details, request_id}}, CORS allow-list, per-user + global rate limits, structured JSON logs carrying request_id.

4. AI engine in detail

Generation and ranking are deliberately separate concerns. A hosted language model writes the copy; our own NumPy/SciPy engine decides which three candidates you see and explains why. That split is what makes the ranking measurable, testable against golden values, and independent of whichever provider is healthy today.

4.1 Provider chain

request
  └─ primary provider (MM_LLM_PROVIDER)      e.g. groq → openai/gpt-oss-120b
       ├─ 401/404/429 → Groq model fallback list (gpt-oss-20b, qwen3.8-27b)
       ├─ 429 quota / 5xx → LLMUnavailable → next configured hosted provider
       └─ breaker open (3 fails / 60 s) → skip provider without a call
  └─ every hosted provider failed
       ├─ MM_ALLOW_TEMPLATE_FALLBACK=true  → template engine, batch flagged is_fallback
       └─ otherwise                        → request FAILED, reason stored, previous batch kept
ConcernImplementation
One call, six candidatesOver-generate six in a single prompt so candidates are comparable and cost stays at one billing unit per batch
PromptSystem + user prompt carrying brief, style arms (tone × structure), three retrieved exemplars, six recent posts, voice notes, banned words, additional instructions
Provenanceprovider, model, source, created_at, fallback_reason persisted per request and rendered in the review header

4.3 Algorithms and their parameters

AlgorithmDefinitionParameters / notes
Feature extractionrelevance = cos(e, q); tone = softmax classifier P(tone); personalisation = ⟨e, u⟩; novelty = 1 − max cos(e, H); length = clipped z-score against learned stats; history = Beta posterior meanEvery feature mapped into [0,1] so the score is interpretable and weights are comparable
Scorings = F · wdefault w = (.30, .20, .20, .15, .10, .05), always non-negative and summing to 1
Constrained gradient stepw ← projsimplex(w + η · ∇w), ∇w = −β(fchosen − Σk pkfk) + 2λ(w − w0)Softmax choice model with inverse temperature β = 8, regularisation λ = 0.005 pulling back toward the default weights, learning rate η = 0.01; projection keeps w non-negative and summing to 1 after every update
Preference vectoru ← (1 − α)·u + α·echosenExponential moving average over chosen/copied candidates; drives the personalisation feature
Thompson samplingθarm ~ Beta(α, β); pick the top three drawsLaplace-smoothed priors per (tone, structure) arm; 2 exploit + 1 explore per batch
MMRargmaxd [λ·rel(d) − (1 − λ)·maxs∈S sim(d, s)]λ = 0.7; greedy and exhaustive variants; style-arm quota prevents three variants of one style
ConfidenceP(rank 1) from 200 Dirichlet draws around w, scoring the feature matrix each drawSeed 42; high / medium / low bands; deterministic for fixed inputs
Wilson interval(p̂ + z²/2n ± z√(p̂(1−p̂)/n + z²/4n²)) / (1 + z²/n)95% default; selection rate, approval rate, top-1 agreement
Tone classifiersoftmax(Wx + b) over eight tone labels800 labelled rows, trained at startup, weights cached to tone_training_model.npz
Deduplicationn-gram Jaccard similarity above threshold → dropOpening-line and full-text variants; near-duplicate check against published history
Occasion gatingrelevance = |name tokens ∩ objective tokens| / |name tokens| ≥ 0.5, or a festive-intent bridge score of 0.5; plus date eligibilityPure and clock-explicit — the caller supplies today in the user's timezone; a past occasion never enters context automatically
Analytics statisticsχ² independence, Shannon entropy, MRR, top-1 agreement, Pearson correlationAll computed per user over their own history, with small-n caveats shown in the UI
Dimensionality reductionPCA to 2-D for the embedding mapDisplayed candidates + intent point + history points, so the user can see the candidate cloud
Determinism: seeded RNG everywhere (Monte-Carlo, Thompson, tone training) — same inputs and weights always produce the same ranking, which is what makes the golden-value suite possible. Model text is not deterministic, which is exactly why the ranking and its explanation are the parts under test.

6. Data layer

  • 16 tables per blueprint Section 9 (listed in §2); portable string enums instead of native PG enums so SQLite and Postgres share one schema.
  • UTC everywhere: a custom UTCDateTime TypeDecorator normalises SQLite's naive datetimes back to aware UTC — no naive/aware mixing bugs.
  • Vectors as float32 BLOBs (vec_to_blob/blob_to_vec); cosine computed in NumPy — identical results on SQLite and Postgres, pgvector-ready for scale.
  • JSON columns where the blueprint allows them: per-request stage trace, six-feature score breakdowns, tone counts, the saved brief and provenance.
  • Portability: psycopg[binary] is a first-class dependency and plain postgresql:// URLs are normalised to postgresql+psycopg:// with TLS, so managed Postgres is a configuration change.

7. Automation (worker)

  • APScheduler ≥3.10: daily cron (timezone MM_SCHEDULER_TIMEZONE) + interval trigger; runs in-process by default, or standalone via python -m app.scheduler.runner (compose and Render do the latter).
  • Jobs: prepare_due_cycles (idempotent — creates the next cycle + generation request), send_reminders (T-3, T-1, NEEDS_ATTENTION nudges), catch_up (missed runs), extend_plans (auto-extend the 12-cycle horizon), all recorded in job_runs for the admin audit.
  • Hosts that suspend background schedulers can drive the same idempotent tick through POST /api/v1/admin/scheduler/run with a shared secret; concurrent ticks are rejected with 409.
  • Cycle state machine: PLANNED → GENERATING → AWAITING_REVIEW → APPROVED → SCHEDULED → PUBLISHED (+ SKIPPED / FAILED).

10. Runtime requirements

  • Dev machine: Python 3.10+ (tested 3.10.11), Node 18+ (tested Node 20/22). No Docker or PostgreSQL needed for SQLite mode.
  • Production: any Docker host — docker compose up --build; or Vercel + Render as deployed (set NEXT_PUBLIC_API_URL, MM_ENVIRONMENT=production, a strong MM_SECRET_KEY and the provider key).
  • Scale path: swap MM_DATABASE_URL → managed Postgres, run multiple stateless API instances, move the worker to its own service (already supported), and enable MiniLM for stronger semantics — no code changes required.
