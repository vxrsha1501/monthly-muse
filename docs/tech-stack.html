2. Architecture (blueprint Section 13)

FRONTEND — Next.js 14 + TypeScript + Tailwind
Dashboard · Create · Review/Compare · Calendar · Plans · History · Analytics · Settings — calls only the public API; no secrets in the browser
│ HTTPS / JSON — JWT access token + refresh cookie ▼
BACKEND API — FastAPI
[Auth + RBAC] → [Validation] → [Routers (61 endpoints)] → [Services] → [uniform error / JSON-logging layer]
▼
AI / NLP PIPELINE — pure NumPy (app/ai/)
preprocess + keywords → context + history retrieval → Thompson-sampled style arms → LLM adapter (retry, breaker, template fallback) → 384-d embeddings → cosine similarity → features F, s = F·w → MMR top-3 → Monte-Carlo confidence → explanation payload
▼
DATABASE — SQLite (default) / PostgreSQL + pgvector
16 tables: users, user_preferences, audience_profiles, topics, occasions, monthly_plans, post_cycles, generation_requests, generated_messages, feedback_events, tone_stats, scheduled_posts, post_metrics, notifications, job_runs, analytics_daily
▲
AUTOMATION — APScheduler worker
daily cycle scan → enqueue generation → notify → T-3/T-1 reminders → catch-up → plan extension · job_runs audit

Statelessness rule from the blueprint is respected: the API holds no in-memory user state, so it can run behind several instances; the worker shares the same code and database but starts with a different command (python -m app.scheduler.runner).

3.3 Security

  • Argon2id password hashing (argon2-cffi), tuned parameters, constant-time compare.
  • JWT access (15 min) in memory + refresh (14 days) in an httpOnly, SameSite cookie; silent refresh in the API client hides 401s.
  • Signed ICS calendar token so subscription URLs work without a login.
  • Uniform error envelope {error: {code, message, details, request_id}}, CORS allow-list, per-user + global rate limits, structured JSON logs carrying request_id.

4. AI / NLP engine in detail

All algorithms are pure NumPy/SciPy and unit-tested against the blueprint's Section 17 golden values.

StageImplementationKey parameters / guarantees
1. Preprocessingai/text.pynormalize → tokenize → lightweight lemma → keyword extraction (TF-IDF-ish scoring), n-gram Jaccard dedup, banned-word & CTA checks
2. Embeddingsai/embedder.py384-d feature hashing with signed weights, L2-normalised; optional MiniLM; vectors stored as float32 BLOBs
3. Similarityai/similarity.pycosine, E·Hᵀ history matrix, novelty = 1 − max cos, PCA 2-D map for the UI
4. Featuresai/features.pyrelevance, tone, personalization ⟨e,u⟩, novelty, length (z-score), history (Beta) → row F ∈ [0,1]⁶
5. Scoringai/scoring.pys = F·w, default w = (.30,.20,.20,.15,.10,.05); constrained gradient step (λ=0.005, β=8, lr=0.01) projected onto the simplex; reason-nudge from reject reasons
6. Diversityai/mmr.pyMMR λ=0.7 with greedy + exhaustive options and style-arm quotas so the top-3 differ
7. Confidenceai/confidence.pyDirichlet Monte-Carlo, 200 seeded samples (seed 42) → P(rank-1) + band; Wilson intervals for rates
8. Armsai/arms.pyThompson sampling over tone × structure arms (Beta priors, 2 exploit + 1 explore), Laplace-smoothed tone suggestions
9. Toneai/tone.pySoftmax logistic regression trained on 800 labeled rows at startup, weights cached to .npz, confusion-matrix helper
10. Generationai/llm_adapters.pyOpenAI/Anthropic/Ollama/Template behind one interface; retry 1s/3s/9s + jitter, circuit breaker 5 fails/60 s, tolerant JSON parse, PRICING cost table
11. Personalizationai/personalization.pyreward model → preference vector u (EMA), Beta arm stats, learned length stats, online weight updates, edit-distance attribution
Determinism: seeded RNG everywhere (Monte-Carlo, Thompson, training) — same inputs and weights always produce the same ranking, which is what makes the golden-value test suite possible.

6. Data layer

  • 16 tables per blueprint Section 9 (listed in §2 above); portable string enums instead of native PG enums so SQLite and Postgres share one schema.
  • UTC everywhere: a custom UTCDateTime TypeDecorator normalises SQLite's naive datetimes back to aware UTC — no naive/aware mixing bugs.
  • Vectors as float32 BLOBs (vec_to_blob/blob_to_vec); cosine similarity computed in NumPy — identical results on SQLite and Postgres, pgvector-ready for V2 scale.
  • JSON columns where the blueprint allows them (tone_counts, per-request stage output) keep reads cheap without a schema change.
  • Alembic 1.13 is installed and the metadata is importable, so alembic revision --autogenerate works out of the box for the Postgres deployment.

7. Automation (worker)

  • APScheduler 3.11: daily cron 02:00 (timezone MM_SCHEDULER_TIMEZONE) + 5-minute interval trigger; runs in-process by default, or standalone via python -m app.scheduler.runner (compose does the latter).
  • Jobs: prepare_due_cycles (idempotent — creates next month's cycle + generation request), send_reminders (T-3, T-1, and NEEDS_ATTENTION nudges), catch_up (missed runs), extend_plans (auto-extend the 12-cycle horizon), all recorded in job_runs for the admin page.
  • Cycle state machine: PLANNED → GENERATING → AWAITING_REVIEW → APPROVED → SCHEDULED → PUBLISHED (+ SKIPPED / FAILED).

10. Runtime requirements

  • Dev machine: Python 3.10+ (tested 3.10.11), Node 18+ (tested 22.19 / npm 10.9). No Docker or PostgreSQL needed for the default SQLite mode.
  • Production: any Docker host — docker compose up --build (Postgres 16, API :8000, worker, frontend :3000); secrets via environment, never in Git.
  • Scale path: swap DB URL → Postgres + pgvector, run multiple stateless API instances, move the worker to its own container (already supported), and enable the MiniLM embedder for stronger semantics — no code changes required.
