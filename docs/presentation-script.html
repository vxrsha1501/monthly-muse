How to use this script

  • SPEAKER A and SPEAKER B mark who owns the slide.
  • Handoff lines (in yellow) are spoken by the named speaker to pass the floor — say them out loud so the audience knows who is talking next.
  • Timings are cumulative from the start. Keep to them; if you run long, trim the roadmap slide, never the demo.

Rehearsal tip: practise the demo transitions once with the site open. The dashboard already shows "November post ready for review (3 candidates)", so the demo starts one click from the review screen.

Slide 4 — How it works (user flow) 2:15 – 3:15

The monthly loop

Product flow3:15
SPEAKER A
"The loop is short. First, you create a Monthly Plan — topic, audience, platform, tone, posting day. Then the scheduler detects the upcoming month, pulls the relevant occasion — Diwali, a seasonal moment — and runs the pipeline automatically."
"You get a notification: three ranked candidates are waiting. You open the review screen, pick one, edit one, or reject one with a reason. You approve it, it lands in the calendar, and it's marked published."
"Every one of those actions is recorded as a feedback event. That's where the learning starts."

Slide 5 — Architecture 3:15 – 4:30

System architecture — three pieces, one database

Engineering4:30
SPEAKER B
"The system is three pieces. A Next.js 14 frontend that only ever talks to the public API — no secrets in the browser. A FastAPI backend with fifty-eight endpoints covering auth, plans, cycles, messages, analytics and the calendar."
"And a scheduler worker running on APScheduler, sharing the same code and the same database but started with a different command. The API is stateless, so it can be scaled by just adding instances."
"Underneath is a sixteen-table schema: users, preferences, audiences, topics, occasions, plans, cycles, generation requests, messages, feedback events, tone statistics, scheduled posts, metrics, notifications, job runs, and a daily analytics rollup."
Handoff — B: "The interesting part is what runs inside that backend. A."

Slide 6 — The AI pipeline 4:30 – 6:00

Fourteen pipeline stages, in one request

Core system6:00
SPEAKER A
"Generation is a fourteen-stage pipeline. It starts by understanding context — plan, audience, occasion, platform — then retrieves your history: your past posts, their embeddings, and what you selected or rejected."
"Next it picks style arms using Thompson sampling, then makes one call to the language model — which over-generates six candidates. One call, six candidates: that's deliberate, it's the cost-efficient way to have something to choose from."
"Then the filter chain. Hard constraints — length limits per platform and language, banned words, emoji level. Deduplication so no two candidates repeat an opening line. Then everything is embedded with our own 384-dimensional embedder."
"We compute six features per candidate, score them, run MMR to make sure the final three are stylistically different, estimate confidence, and produce an explanation payload — which is what you actually see on screen."
Handoff — A: "Now the maths. B."

Slide 7 — The maths 6:00 – 7:30

Scoring: s = F · w, then MMR, then confidence

Mathematical core7:30
SPEAKER B
"Each candidate is a row of six features: relevance, tone, personalization, novelty, length and history. The score is a dot product — s equals F times w — with default weights of point three, point two, point two, point one five, point one and point oh five."
"The score alone would give you three near-identical posts. So we add MMR — maximal marginal relevance — at lambda zero point seven, which trades relevance against diversity. That's why candidate three is tagged 'exploring a new style'."
"Confidence comes from a Dirichlet Monte-Carlo simulation: two hundred seeded draws, so the same inputs always give the same answer. For rates in the analytics we use Wilson intervals, because a naive percentage lies when n is small."
Handoff — B: "Rather than describe the output, let's show it. A drives the demo."

Slide 14 — Q&A preparation

Anticipated questions, with the suggested answer and who should take it.

QuestionWhoSuggested answer
Why is the generated text a bit awkward?A"The demo runs on the offline template engine so it costs nothing and works without keys. The OpenAI/Anthropic/Ollama adapters are built and tested — we add a key and the same six candidates come from a real model. Everything downstream — scoring, ranking, personalization — is identical."
Why not just use ChatGPT?B"A single model call gives you one answer with no ranking and no memory. We over-generate six, then filter, embed, score and diversify with our own engine — and every user action feeds back into next month's ranking. The model is one component, not the product."
How is this different from a prompt?B"A prompt has no state. Ours has a preference vector, Beta statistics per style arm, learned length stats and a weight vector that updates with a constrained gradient step — all visible in Settings."
Is it really automatic?A"Yes — APScheduler runs a daily scan, creates the cycle for the upcoming month, gathers the occasion context, generates, and notifies at T-3 and T-1 days. Preparation is idempotent, so a restart can't duplicate anything."
Why SQLite and not PostgreSQL?A"The target machine has no Docker or Postgres. The schema is portable — string enums, UTC-normalised timestamps, vectors as float32 blobs — so setting MM_DATABASE_URL to a managed Postgres is the only change. That's the deployment plan."
Isn't 22% selection rate low?B"n is nine, so the Wilson interval is six to fifty-five percent — too early to read as a quality signal. It's also counting 'left unselected' events. The metric exists precisely so we don't over-claim from small numbers."
How do you stop it repeating itself?B"Three ways: n-gram Jaccard deduplication at generation, cosine similarity against your full history with a novelty feature in the score, and MMR so the three shown are stylistically distinct. There's also a repetition alert in analytics at cosine 0.85."
What about privacy / API keys in the browser?A"The frontend only calls the public API and holds no secrets. Refresh tokens are httpOnly cookies; passwords are Argon2id. Secrets live in platform environment variables, never in the repository."
What's the hardest part you'd redo?Either"Getting the golden tests written first. Several real bugs — candidates never being embedded, a naive/aware datetime mix, MMR returning two candidates from the same style arm — were caught by those tests before they could reach the UI."
Can it handle multiple users?A"Yes — every query is scoped to the authenticated user, there's per-user rate limiting, and the API is stateless so instances can be added behind a load balancer. The scheduler worker is separate and shares only the database."
